# LMS-004 — User Model

Status: CODE COMPLETE

## Goal

Establish and verify `User` as the identity foundation while preserving the approved LMS-002 schema and LMS-003 database conventions. This ticket does not implement authentication, authorization, or user management.

## Scope

- Verify the required UUID primary key, email, optional name, `createdAt`, and `updatedAt` fields.
- Preserve the existing email unique constraint and `OrganizationMembership` relation.
- Clarify current email uniqueness and defer any normalization or case-insensitive identity policy to a future explicit decision.
- Keep the existing migration history unchanged if it already satisfies these requirements.

## Out of scope

- Authentication, credentials, sessions, tokens, OAuth, MFA, verification, login, or signup.
- Roles, permissions, authorization, tenant enforcement, membership workflows, user APIs, or user management UI.
- Additional models or fields beyond the established User foundation.

## Findings

- The existing `User` model has a required UUID primary key generated with the established Prisma `uuid()` strategy, required `email`, optional `name`, required timestamps, and the existing memberships relation.
- The LMS-002 migration already creates the required `User` columns, `User_pkey`, `User_email_key`, and membership foreign key. No schema change or new migration is needed.
- Email uniqueness follows the configured PostgreSQL collation. The schema does not normalize addresses or explicitly provide case-insensitive uniqueness; a future feature must make that policy explicit before relying on it.
