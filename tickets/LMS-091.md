## Implementation notes

- The UI uses only `/api/organizations/teams`, `/api/organizations/teams/:teamId`, `/api/organizations/teams/:teamId/members`, `/api/organizations/teams/:teamId/members/:employeeId`, and the existing `/api/organizations/employees` list.
- Team and employee searches filter only the bounded records returned by their APIs. No client-side search is presented as a complete organization-wide search.
- New membership choices require an active employee from the loaded employee list. Existing members are removed from the choices; the API remains authoritative for races, inactive employees, and invalid/foreign IDs.
- The list API internally selects the member's global user ID only to apply LMS-090 field visibility. The route strips it before serialization and removes job title and department for a MEMBER reading another employee.
- The production membership read now scopes one Team query by both `teamId` and trusted `organizationId`, then selects its active OrganizationMembership relations. An existing Team with no membership rows produces `members: []`; only a missing Team in that tenant produces `team_not_found`.
- Team deletion relies on the existing database cascade for TeamMembership rows. Employee accounts and OrganizationMembership rows are not deleted.
- The UI reuses the existing Course Builder dialog focus, keyboard, dirty-close, and toast patterns. No dependency, schema, migration, authentication, session, role, or database model change was required.
- The Team overview uses an inline accessible Users icon; no icon package was added.

## COO local acceptance defect — membership read

The CEO reported that an existing Team opened with its name and description, while the member section said “This team is no longer available in your organization” and disabled **Add employee**.

Code-path findings:

- Team detail, team members, and employee list are separate same-origin requests. They resolve the authenticated user's server-verified default organization and use the shared Prisma client. No client-provided organization selection or authorization bypass was added.
- Before this correction, the membership list used an interactive transaction with a separate Team existence query followed by the active-members query. The empty members query itself returns `[]`; it does not establish Team existence.
- The UI mapped every HTTP 404 to “This team is no longer available,” even when a 404 body did not contain `team_not_found`. Thus that UI text alone did not prove the Team or the user's organization membership was missing.
- The CEO's original three HTTP response bodies were not available to this task, and the `lms_platform` database was not accessed. The precise source of the locally reported 404 therefore remains an evidence gap rather than an inferred loss of organization membership.

Correction:

- Replaced the two-step transactional membership read with one tenant-scoped Prisma Team query and its active-member relation. This keeps Team existence independent from the number of memberships and returns `[]` for a persisted empty Team.
- The UI now distinguishes a response body with `error: "team_not_found"` from other 404s. It preserves distinct 401, 403, 404, and 503 messages.
- Added a PostgreSQL-backed test for a persisted empty Team and a Playwright regression that compares live responses from team detail, members, and employee list, then adds/removes a member and reloads the Team detail page.

Verified isolated endpoint contract: the Playwright scenario against `lms_platform_e2e` recorded team detail `200` with a `{ team }` body; empty members `200` with exactly `{ members: [] }`; and employee list `200` with an `{ employees: [...] }` body. Adding an active employee returned `201`; the populated list returned `200` with that employee's ID and email; removing returned `200`; and the list returned `200` with `{ members: [] }` again. The Team detail page loaded before and after browser reload, with **Add employee** enabled for the empty and populated Team. Existing API coverage verifies unauthenticated `401`, MEMBER mutation `403`, foreign/missing Team `404` with the same `{ error: "team_not_found" }` body, inactive employee `404`, and storage failure `503`.
