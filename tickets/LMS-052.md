## Architecture and implementation

- `TransactionalEmailProvider` is the replaceable boundary; `createBrevoEmailProvider` makes one authenticated request to `POST /v3/smtp/email` using native `fetch`.
- `employeeInvitationDelivery` adapts LMS-014's existing interface and reads server-only configuration at send time. An unavailable configuration prevents invitation creation.
- The invitation page remains `/auth/activate`; the raw bearer token remains in the fragment. Only the preexisting SHA-256 digest is persisted.
- A provider 2xx response means Brevo accepted the request for processing. It is not proof that the recipient received it. No automatic retry or provider webhook is included.
- Failed sends invalidate the newly created invitation through the existing LMS-014 path. A later administrator retry creates a replacement and makes the older token unusable.
- The employee profile button does not reveal invitation status or credentials and is shown only for active MEMBER memberships. Server authorization remains authoritative.

## Known limitation and acceptance risk

A network timeout can happen after Brevo accepts a message but before the application receives the response. The application reports failure and invalidates that invitation; the recipient might then receive an unusable link. Do not automatically retry an ambiguous send. Provider-side delivery events and a durable email outbox remain future work. A live test also depends on the separately approved Brevo account, sender-domain verification, and DPA/privacy decision.
