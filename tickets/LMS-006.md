# LMS-006 — Organization Membership

Status: CODE COMPLETE

## Objective

Establish and verify `OrganizationMembership` as the explicit persisted association between a `User` and an `Organization`, while preserving the approved LMS-002 database foundation.

## Scope

- Verify the membership model's identifiers, role, timestamps, relations, uniqueness, index, foreign keys, and delete behavior.
- Preserve `User.memberships`, `Organization.memberships`, and the explicit join model.
- Document membership and role responsibility in `docs/database.md`.
- Keep the existing schema and migration history unchanged if they already satisfy the requirements.

## Out of scope

- Authentication (LMS-007), authorization enforcement (LMS-008), tenant context (LMS-009), or tenant isolation (LMS-010).
- Employee management (LMS-012), employee invitations (LMS-014), membership CRUD, APIs, UI, or any other product workflow.
- Permission matrices, RBAC enforcement, PostgreSQL RLS, or changes to `OrganizationRole`.

## Implementation findings

- `OrganizationMembership` already has a UUID primary key, UUID `userId` and `organizationId`, required `role` defaulting to `MEMBER`, and required `createdAt` and `updatedAt` fields.
- Required `user` and `organization` relations connect each membership to `User` and `Organization`; `User.memberships` and `Organization.memberships` preserve both relation collections.
- `@@unique([userId, organizationId])` makes duplicate membership records for the same user and organization impossible at the database level.
- `@@index([organizationId, role])` supports membership queries by organization and role. The unique composite index is also usable for `userId`-leading lookups.
- `OrganizationRole` remains unchanged and contains `OWNER`, `ADMIN`, and `MEMBER`. The role is a structural attribute of the membership; it has no permission semantics or authorization enforcement in this ticket.
- The existing model is an explicit association. No implicit many-to-many relation or membership workflow was added.

## Migration findings

- The LMS-002 foundation migration already creates the membership UUID primary key, UUID foreign keys, `OrganizationRole` column with `MEMBER` default, timestamps, composite unique index, organization/role index, and foreign-key constraints.
- Both foreign keys use `ON DELETE CASCADE ON UPDATE CASCADE`. This matches the existing LMS-002 foundation and is preserved.
- Prisma's schema-to-SQL migration diff matches the committed LMS-002 migration. The schema required no change, so no new migration was created; editing the applied foundation migration was unnecessary.
- No live PostgreSQL migration or migration-status test was run because a database connection was not available.
