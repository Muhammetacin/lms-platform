# LMS-007 — Authentication

Status: CODE COMPLETE

## Objective

Establish a secure server-side authentication foundation that identifies a `User` and maintains an authenticated application session without implementing authorization or tenant context.

## Scope

- Add password credential persistence without changing the existing user profile or LMS-002 migration.
- Verify email/password credentials with generic failures.
- Create, look up, expire, and invalidate opaque server-managed sessions.
- Provide `getAuthenticatedUser()` as the server-side identity operation.
- Protect the cookie-authenticated login/logout routes against cross-origin form requests.
- Document architecture, limits, security, migration, and future ticket boundaries; record the security decision in ADR-004.

## Out of scope

- Authorization, RBAC, role checks, permission matrices, membership access checks, or authorization middleware (LMS-008).
- Active organization/tenant context (LMS-009), tenant isolation, or PostgreSQL RLS (LMS-010).
- Public registration, credential provisioning UI, password reset, email verification, invitations, MFA, OAuth/social login, SSO, organization switching, or unrelated UI.
- Shared brute-force rate-limiting infrastructure (follow-up LMS-060).

## Architecture decision

Use a narrow custom email/password and database-session implementation on the existing Next.js App Router, Node.js crypto, and Prisma/PostgreSQL stack. The repository has no approved/configured identity provider or authentication library. The decision and alternatives are in [ADR-004](../docs/decisions/ADR-004-authentication.md); the operational security model is in [Authentication](../docs/authentication.md).

## Implementation

- Added `PasswordCredential` as a separate one-to-one relation to `User`; passwords use versioned `scrypt` hashes with a random salt, 64-byte key, and constant-time verification.
- Added `Session` with a 7-day explicit expiry. Login generates a random 32-byte token for the cookie and stores only its SHA-256 digest.
- Added same-origin JSON login and logout Route Handlers. Login trims surrounding email whitespace and preserves email casing; unknown account and incorrect password both return the same generic 401.
- Added `getAuthenticatedUser()` returning only `{ id, email, name }` or `null`. It does not evaluate permissions, role, membership, or tenant.
- Added a server-only `provisionUserPassword()` helper for trusted future provisioning; it is not exposed through a public account-creation endpoint.
- Production cookie is `__Host-lms_session`, `HttpOnly`, `Secure`, `SameSite=Lax`, path `/`, with explicit expiry; development uses `lms_session` over HTTP.
- No signup or credential provisioning workflow is added. Existing users without a `PasswordCredential` cannot log in.

## Database changes

- Added the `PasswordCredential` and `Session` models, unique constraints, expiry index, and cascading user foreign keys.
- Added migration `20261004120000_authentication_sessions_credentials` with reviewed SQL.
- Existing LMS-002 migration is unchanged. `NEXT_PUBLIC_APP_URL` is the only auth request configuration and already exists in `.env.example`; no session secret is needed because session tokens are random and only their digests persist.

## Security model

- Password hashes use Node.js `scrypt` (`N=32768`, `r=8`, `p=1`, 16-byte random salt, 64-byte result; 64 MiB maxmem). Passwords are not logged, returned, trimmed, or normalized.
- Opaque 256-bit session token is returned only in a cookie. Database stores SHA-256 digest only; fixed session lifetime is seven days; logout deletes the server-side row; expired sessions are rejected.
- Cookie uses `HttpOnly`, production `Secure`, `SameSite=Lax`, path `/`, and fixed expiry. Login/logout require exact `Origin` matching `NEXT_PUBLIC_APP_URL` and JSON content type; login body is bounded to 8 KiB.
- Unknown account and incorrect password return the same `401 invalid_credentials`; malformed input and internal failures return generic responses.
- No shared rate limiter or trusted client-IP contract exists. A process-local limiter would not protect multiple instances, so brute-force protection is documented as a required LMS-060 follow-up; the endpoint is not claimed to be ready for public production exposure without it.

## Assumptions

- LMS-007 allows a narrow custom implementation because no auth provider/library or account provisioning policy is approved/configured in the existing repository.
