# LMS-014 — Employee Invitation / Account Activation

Status: DONE

> Historical governance backfill: this ticket record was added after LMS-014 had already been implemented, QA/security-reviewed, and merged into `main`. It completes the repository's LMS ticket records; it does not represent new product work.

## Objective

Safely invite an existing active `MEMBER` employee who has no `PasswordCredential` to activate their account and set an initial password. The invitation is scoped to the employee's organization membership while the associated `User` remains the global identity.

LMS-014 is account activation for an eligible employee. It is not password reset, role management, or a general invitation system.

## Domain model

`EmployeeInvitation` is a one-time, tenant-scoped bootstrap credential with these fields:

| Field | Purpose |
| --- | --- |
| `id` | Invitation record identifier. |
| `userId` | Global `User` identity being activated. |
| `organizationId` | Organization that owns the invited membership. |
| `membershipId` | Target `OrganizationMembership` employee record. |
| `tokenHash` | SHA-256 digest of the invitation token; the raw token is never persisted. |
| `expiresAt` | Expiration timestamp, 72 hours after issuance. |
| `consumedAt` | Set when the invitation is used or invalidated. |
| `createdAt` | Record creation timestamp. |
| `updatedAt` | Last record update timestamp. |

The record relates to `User`, `Organization`, and `OrganizationMembership`. The `userId`, `organizationId`, and `membershipId` references must agree with one another. Activation rechecks this relationship against the membership before creating credentials.

The invitation belongs to `OrganizationMembership`, which is the tenant-specific employee identity. `User` remains the global authentication identity and may have memberships in more than one organization.

## Authorization and invitation eligibility

The administrator endpoint is:

```text
POST /api/organizations/employees/:employeeId/invitation
```

It uses the trusted tenant context and the existing `MANAGE_MEMBERS` capability:

| Role | Invite |
| --- | --- |
| `OWNER` | Yes |
| `ADMIN` | Yes |
| `MEMBER` | No |

The target must be an active `MEMBER` in the caller's trusted organization and must not already have a `PasswordCredential`. Cross-tenant and missing employee IDs use the same safe 404 semantics. The endpoint does not trust a client-provided organization or tenant ID.

## Re-invitation

Creating a replacement invitation runs in a PostgreSQL `SERIALIZABLE` transaction. It consumes or invalidates any earlier unused invitation for the same employee before creating the replacement, so two invitations for one target cannot remain concurrently usable.

Deactivating the target membership also makes its invitation invalid. Activation checks that the membership is still active and consistent with the invitation before changing credentials.

## Activation APIs

The public activation endpoints do not require an existing authenticated session:

```text
POST /api/auth/invitations/validate
POST /api/auth/invitations/activate
```

They accept the invitation token and, for activation, the initial password. They do not trust client-provided organization or tenant data. The organization and membership are derived entirely from the invitation record and its verified relationships.

## Atomic activation flow

Activation performs the following checks and changes in order:

1. Look up the invitation by the hash of the supplied token.
2. Confirm the invitation is valid, unexpired, and not already consumed.
3. Confirm `userId`, `organizationId`, and `membershipId` still describe the same membership.
4. Confirm the membership is active and has role `MEMBER`.
5. Confirm the user does not already have a `PasswordCredential`.
6. Validate and hash the initial password.
7. Consume the invitation and create the `PasswordCredential` in one transaction.

Invitation consumption and credential creation are atomic. A database failure cannot leave a half-consumed invitation or a credential created without consuming that invitation. Concurrent activation attempts cannot both succeed; the invitation is one-time use.

## Password security

LMS-014 reuses the LMS-007 password helpers `isPasswordValid()` and `hashPassword()`. It introduces no second password policy and never overwrites an existing credential. Password reset remains a separate feature.

## Token handling

- Tokens use cryptographically secure randomness with 256 bits of entropy and are encoded as Base64URL.
- Only the SHA-256 token hash is stored in the database; the raw token is never persisted or logged.
- The activation URL carries the token in its URL fragment, so the browser does not send it in the initial HTTP request.
- The raw token is not returned through the administrator API.
- Activation pages set `Referrer-Policy: no-referrer`; responses use `Cache-Control: no-store`.
- Invitations expire after 72 hours and can be consumed only once.

## Delivery and audit dependencies

Email delivery belongs to LMS-052. LMS-014 defines a narrow invitation-delivery interface but does not build a fake mailer. Until a real adapter is available, production delivery reports unavailable and invitation creation does not pretend an email was sent.

Audit logging belongs to LMS-058. LMS-014 does not add a parallel audit subsystem; audit-event integration remains dependent on LMS-058.

## Tests

Coverage includes authorization and tenant scoping, cross-tenant employee protection, missing and invalid employee IDs, inactive memberships, and the `OWNER`/`ADMIN` versus `MEMBER` permission boundary. Invitation tests cover existing credentials, replacement invitations, expiry, consumption, and invalidation after membership deactivation.

Activation coverage includes credential creation with the existing password helpers, protection against overwriting an existing credential, concurrent activation, one-time use, transactional rollback, forged tenant input, and PostgreSQL integration against the production persistence path.

## Out of scope

- Password reset.
- Role management and invitations for `OWNER` or `ADMIN`.
- Microsoft or Google SSO.
- MFA.
- A production email provider, general notification system, or fake mailer.
- An audit subsystem separate from LMS-058.
- Automatic login after activation.
