# LMS-020 — Course Modules

Status: CODE COMPLETE — READY FOR QA/SECURITY REVIEW

## Objective

Introduce tenant-owned Course Modules as the ordered structural children of a Course, with PostgreSQL-enforced tenant integrity and an admin management API.

## Product decisions

- A Course may contain zero Modules; there is no minimum count.
- Module titles are not unique.
- Position is one-based, contiguous after successful API create/move/delete, and cannot be set through create or PATCH.
- Only a DRAFT Course may have its Module structure created, updated, moved, or deleted. PUBLISHED reads remain allowed and writes return `409 published_course_structure_locked`.
- OWNER and ADMIN use the existing `MANAGE_COURSES`; MEMBER is denied.
- LMS-021 owns Lessons; LMS-023 owns publishing; LMS-058 owns audit integration.

## Database model

`CourseModule` stores UUID ID, `organizationId`, `courseId`, `title`, nullable `description`, integer `position`, `createdAt`, and `updatedAt`. It has `@@unique([id, organizationId])`, `@@unique([courseId, position])`, and an organization/course/position list index. A migration CHECK enforces `position >= 1`.

The model has a direct cascading Organization FK and a composite cascading `(courseId, organizationId) → Course(id, organizationId)` FK. PostgreSQL therefore rejects a direct Module insert that pairs Course A with Organization B. The composite Module candidate key is ready for an LMS-021 Lesson FK.

## API

- `GET /api/organizations/courses/:courseId/modules`
- `POST /api/organizations/courses/:courseId/modules`
- `GET /api/organizations/courses/:courseId/modules/:moduleId`
- `PATCH /api/organizations/courses/:courseId/modules/:moduleId`
- `POST /api/organizations/courses/:courseId/modules/:moduleId/move`
- `DELETE /api/organizations/courses/:courseId/modules/:moduleId`

Responses expose `id`, `title`, `description`, `position`, `createdAt`, and `updatedAt`, and set `Cache-Control: no-store`. Create accepts title and optional description only; PATCH accepts title and/or description only; move accepts integer position only. Titles and descriptions use Course-style trimming, Unicode code-point limits, control character checks, and unpaired-surrogate rejection. Unknown and tenant/identity fields are rejected.

## Ordering

Create allocates `MAX(position) + 1` inside a transaction. Move positions must be in `1..moduleCount`; moving a Module shifts intervening rows and preserves IDs and timestamps. Delete closes the gap atomically. Moving to the current position is a no-op. Delete of the sole Module leaves a valid empty Course.

## Authorization and tenant isolation

Handlers derive tenant context from the authenticated membership and require `MANAGE_COURSES`. Every query scopes by trusted `organizationId` and route `courseId`; detail and mutation queries also scope by `moduleId`. Foreign Course IDs return `course_not_found`. Missing, foreign-tenant, wrong-Course, and malformed Module IDs return `module_not_found`. PostgreSQL independently enforces Course/Organization consistency through the composite FK.

## Published Course behavior

The production store locks the scoped Course row with `SELECT ... FOR UPDATE` before each structural mutation, then reads status and makes all changes while holding the lock. This serializes structure writes against publication and other structure writes. LMS-023 must use the same Course row lock before changing status and evaluating publication completeness.

## Concurrency

All API structure changes for one Course acquire the parent row lock before computing or changing positions. This makes concurrent creates, moves, and mixed move/create calls execute in a serial order. Move uses an unused positive sentinel, then moves one row at a time in the safe direction to avoid transient `(courseId, position)` unique conflicts. Delete and compaction use the same transaction. Raw position-only updates preserve timestamps. A forced PostgreSQL trigger error verifies transaction rollback without partial reordering.
