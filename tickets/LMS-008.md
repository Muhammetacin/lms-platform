# LMS-008 — Authorization

Status: CODE COMPLETE

## Objective

Establish a centralized, server-side authorization foundation that determines what an authenticated user may do within one explicitly supplied organization, using the existing `OrganizationMembership.role` values.

## Scope

- Build on LMS-007's `getAuthenticatedUser()` without handling cookies, sessions, or password verification again.
- Verify membership for the exact authenticated user and requested organization.
- Centralize `OWNER > ADMIN > MEMBER` hierarchy and the initial organization capability mapping.
- Provide mandatory server-side `require*` checks and a non-throwing `can()` query for UX only.
- Define generic, fail-closed authorization errors and document LMS-007/LMS-009/LMS-010 boundaries.
- Preserve the Prisma schema and migration history.

## Out of scope

- Tenant context or organization switching (LMS-009), tenant isolation or PostgreSQL RLS (LMS-010).
- Platform-admin roles, new role models, role or membership schema changes.
- Employee, team, course, report, settings, invitation, or other future product features.
- Authentication/session changes or new protected APIs and routes.

## Architecture

- `src/lib/authorization.ts` is a `server-only` interface that obtains identity from LMS-007 and queries the shared Prisma client.
- `src/lib/authorization-core.ts` centralizes membership decisions, role ranking, permission mapping, and authorization errors in a database-independent core.
- Membership lookup filters by both `userId` from the authenticated identity and the explicit `organizationId`, selecting only the stored role.
- `requireAuthenticatedUser()`, `requireOrganizationMembership()`, `requireOrganizationRole()`, and `requireOrganizationPermission()` stop protected server work on failure. `can()` returns `false` on any failure and is for UX only.
- No current organization-scoped product route or mutation exists, so no route behavior was changed. Existing login/logout routes remain authentication endpoints.

## Authorization matrix

| Capability | OWNER | ADMIN | MEMBER |
| --- | ---: | ---: | ---: |
| View organization | ✅ | ✅ | ✅ |
| View own membership | ✅ | ✅ | ✅ |
| Manage organization settings | ✅ | ✅ | ❌ |
| Manage members | ✅ | ✅ | ❌ |
| Manage teams | ✅ | ✅ | ❌ |
| Manage courses | ✅ | ✅ | ❌ |
| Assign training | ✅ | ✅ | ❌ |
| View organization reports | ✅ | ✅ | ❌ |
| Manage organization ownership | ✅ | ❌ | ❌ |

The hierarchy is centralized: OWNER satisfies every lower role; ADMIN satisfies ADMIN and MEMBER; MEMBER satisfies MEMBER only. "View own membership" does not grant access to another user's membership. This is an initial policy foundation; the listed future product features were not implemented.

## Implementation

- Reused the existing `OrganizationRole` enum: no schema changes or migration.
- Added explicit UUID organization-context validation and exact composite membership lookup.
- Added stable failure codes: unauthenticated (401), generic forbidden (403), and authorization unavailable (503). Lookup errors and unknown stored roles fail closed without exposing database details.
- Added 11 behavioral authorization tests and included them in GitHub Actions CI.
- Updated product, authentication, and database documentation; added the authorization reference and ADR-008.

## Tests

`tests/authorization.test.ts` exercises missing/authenticated identity, membership and non-membership, database failures, each role hierarchy edge, separate roles for multiple organizations, forged client role claims, missing organization context, capability checks, and unknown database roles.

## Security review

- Authentication remains owned by LMS-007. The authorization layer does not inspect cookies, tokens, or credentials.
- Role comes only from the server-side membership query scoped by authenticated `userId` and explicit `organizationId`; browser-provided roles are ignored.
- Unauthenticated, unauthorized, and unavailable outcomes are distinct. Organization, membership, and database details are not included in generic errors.
- `can()` denies on failures and is documented as UX-only; mandatory operations must use server-side `require*` checks.
- No tenant context, cross-organization data enforcement, RLS, or tenant-isolation claim was introduced. LMS-010 remains responsible for that boundary.
- CI includes the new authorization suite; existing checks were retained.

## Documentation

- Added `docs/authorization.md` for architecture, role semantics, hierarchy, matrix, errors, enforcement, and LMS boundaries.
- Added [ADR-008](../docs/decisions/ADR-008-authorization.md) for the centralized authorization decision.
- Updated product vision, authentication, and database conventions to point to LMS-008 and preserve separation of responsibilities.

## Assumptions

- The authenticated user ID returned by LMS-007 is trusted; membership role is fetched fresh for the requested organization.
- Organization IDs are the existing canonical UUID primary keys. Invalid or absent context receives the same generic 403 as other denials.
- Future organization-scoped routes and mutations will map `AuthorizationError.status` and `.code` appropriately and call a `require*` check at the protected operation.

## Blockers
