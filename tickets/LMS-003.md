# LMS-003 — Base Database Conventions

Status: CODE COMPLETE

## Goal

Establish actionable database conventions before identity/access and product work, while preserving the LMS-002 database foundation and adding no LMS functionality.

## Scope

- Document naming, IDs, timestamps, nullability, enums, relations, delete behavior, unique constraints, and indexes.
- Document Prisma client/database access, transactions, error handling, query selection, filtering, and list pagination conventions.
- Document migration discipline, seed strategy, database testing expectations, and future tenant-context requirements.
- Update `docs/database.md` and record decisions in an ADR.

## Constraints

- Product schema remains only `User`, `Organization`, and `OrganizationMembership`; no LMS-004 or later functionality.
- Preserve LMS-002's UUID strategy, timestamp fields, relationships, migration history, and server-only Prisma client unless a required change is identified.
- Do not claim that LMS-003 provides tenant isolation. Tenant-owned entities must have explicit organization relationships where appropriate; future tenant context must be derived from authenticated server-side context, never arbitrary client-provided IDs. LMS-010 owns enforcement.
- Do not add a migration solely for documentation or invent schema changes.
- Do not mark the ticket QA, APPROVED, or DONE.

## Acceptance criteria

- [x] Database conventions are explicit, concise, and consistent with the LMS-002 foundation.
- [x] `docs/database.md` covers all conventions in scope, including safe DB access, migration discipline, transactions, errors, queries, pagination, seeds, tests, and future tenant context.
- [x] ADR-003 records the decisions without duplicating the operational guidance.
- [x] The schema remains limited to the three foundation models; existing relationships and constraints remain correct.
- [x] No unnecessary migration, product functionality, secrets, or tenant-isolation claims are introduced.
- [x] Relevant lint, typecheck, build, tests, Prisma schema validation, and applicable migration validation pass.
- [x] Ticket is marked CODE COMPLETE after implementation and verification; QA review remains separate.
