# LMS-017 — Employee Import

Status: CODE COMPLETE — READY FOR QA/SECURITY REVIEW. Implementation and PostgreSQL CI pass; independent review and merge are still pending.

## Objective

Allow authenticated OWNER and ADMIN users to create up to 500 employees in their trusted active organization from one CSV upload. Reuse `User` and `OrganizationMembership`; do not update existing employees or create an import/history model.

## Product decisions

- Create-only: no profile update, reactivation, role change, or membership upsert.
- Every created membership has `role = MEMBER` and `active = true`.
- Reuse the exact global `User.email` identity if present. Do not mutate the existing `User` or any other organization's membership.
- A membership in the current organization is an `employee_already_exists` conflict. Employee numbers are unique only in that organization and use the existing PostgreSQL unique constraint.
- A batch with any invalid row, duplicate, or visible tenant conflict creates zero employees. A database or concurrency failure rolls back the complete transaction.
- No credential, invitation, email, TeamMembership, import-history, retention, or custom audit side effects. LMS-058 remains the future shared audit dependency.

## CSV format

The multipart request has exactly one `file` field. The CSV starts with an exact, case-sensitive header row; header order is flexible.

```csv
email,name,jobTitle,department,phone,employeeNumber
jane@example.com,"Doe, Jane",Teacher,Learning,+32 2 555 01 23,EMP-001
```

Required columns: `email`, `name`. Optional columns: `jobTitle`, `department`, `phone`, `employeeNumber`. Unknown, duplicate, or missing-required headers are rejected. Blank optional cells become `null`. The parser is `csv-parse@7.0.3` (`csv-parse/sync`), a direct MIT-licensed dependency with no runtime dependencies. It supports quoted values, quoted commas, escaped quotes, LF/CRLF, UTF-8, and UTF-8 BOM.

## Validation and response

- Email and name reuse LMS-012 normalization; profile fields reuse LMS-013 validation.
- Name: trim, 2–120 Unicode code points, no control characters or unpaired surrogates.
- Optional profile fields: trim, preserve case, at most 120 Unicode code points, no control characters; blank cells normalize to `null`.
- Duplicate CSV emails and duplicate nonblank CSV employee numbers reject all matching rows.
- Maximum file size: 1 MiB. Maximum data records: 500. The request body is read through a bounded reader before multipart or CSV parsing; CSV records are bounded too.
- Row errors contain safe `{ row, field, code }` values and are capped at 100. Row 1 is the header, the first employee is row 2, row numbers count CSV records, and row 0 denotes a file-level error.
- Invalid input returns `employee_import_invalid`; current-organization conflicts return 409 `employee_import_conflict`. Success returns only `{ "imported": number }`. All responses set `Cache-Control: no-store` and contain no CSV values or database internals.

## Authorization and tenant isolation

`POST /api/organizations/employees/import` uses the existing trusted-request check extended to require the `multipart/form-data` media type and the existing same-origin `Origin` check. It then calls `requireTenantContext()` and `MANAGE_MEMBERS`. OWNER/ADMIN are allowed, MEMBER receives 403, and an unauthenticated same-origin caller receives 401.

The store receives only `tenant.organizationId`. CSV headers, form fields, filename, query, and headers never choose the tenant. Organization-owned preflight and writes are scoped to that trusted organization. A global user found by exact email can be associated with memberships in multiple organizations; the import does not read or write foreign membership profile/active/role/team state. A matching employee number in another organization is allowed.

## Transaction semantics and concurrency

The production store performs current-tenant email/employee-number conflict checks, missing global user inserts (`skipDuplicates` only on exact global email), user-ID resolution, and all membership inserts in one PostgreSQL `SERIALIZABLE` transaction. Membership inserts explicitly set the trusted organization, `MEMBER`, `active: true`, and validated profile fields. Existing membership rows are never updated.

Database unique constraints remain authoritative for races with another import or manual employee creation. A unique/serialization failure rolls back the transaction, rechecks current-tenant conflicts, maps visible conflicts to safe row errors, and retries once where appropriate. A repeated/unclassified failure returns a generic 503. There is no migration or schema change.
