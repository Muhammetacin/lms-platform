## Authentication and routing

- `/login` submits JSON to the existing `POST /api/auth/login`. It keeps credentials out of the URL and browser storage and relies on the existing HttpOnly session cookie.
- Existing generic credential errors are presented as **Email or password is incorrect.** Invalid requests and unexpected errors use a generic sign-in message; `authentication_unavailable` has a temporary-unavailable message.
- An authenticated visit to `/login` redirects server-side to `/admin`. `/` redirects server-side to `/login` or `/admin`; no redirect query parameter is accepted.
- Sign out calls the existing `POST /api/auth/logout` with `{}`. A failure keeps the current page visible and displays a generic error.
- The existing password hashing, session, cookie, Origin/CSRF trust, login/logout handlers, and credential error behavior remain the source of truth. No second auth stack or provider was added.

## Admin access, shell, and data

- `/admin` and `/admin/courses` use dynamic server rendering and enforce `requireTenantContext()` followed by `requireOrganizationPermission(tenant.organizationId, "MANAGE_COURSES")` before loading Organization or Course data.
- OWNER and ADMIN are allowed. MEMBER and users with missing/inactive memberships receive a safe access-unavailable view. Unauthenticated requests redirect to `/login`.
- The responsive shell shows the current user, tenant-scoped Organization name, OWNER/ADMIN role, working Dashboard and Courses links, and Sign out control. Active navigation follows the current route path.
- The dashboard counts Courses with Organization-scoped database queries. `/admin/courses` reuses the production Course list service, including `createdAt DESC, id DESC` ordering, and shows title, status, update time, published date, and the existing `/courses/:courseId/preview` link.
- The overview is read-only. Its empty state points to the next Course UI milestone.
- Admin pages export `dynamic = "force-dynamic"` and `revalidate = 0`; the build confirms these routes are server-rendered on demand.

## Local development bootstrap

`pnpm dev:bootstrap` reads only `DATABASE_URL` and the `DEV_BOOTSTRAP_*` settings from `.env.local` (then `.env`). It never falls back to `TEST_DATABASE_URL`. It creates User, PasswordCredential, Organization, and an active OWNER membership in one transaction, hashes with the existing `hashPassword()` implementation, and prints no password. Production-like environment markers are rejected before database access.

The command is idempotent for the matching existing setup, preserves existing credentials, and fails without mutation when an email or Organization slug belongs to an unexpected setup. Prisma CLI now loads `.env.local` before `.env` so the documented `pnpm db:migrate:deploy` flow works with the local file.

See [`docs/local-admin-smoke-test.md`](../docs/local-admin-smoke-test.md) for the 10-step local browser flow.
