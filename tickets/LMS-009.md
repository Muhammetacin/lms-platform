# LMS-009 — Tenant Context

Status: CODE COMPLETE

## Objective

Establish a trusted server-side mechanism for determining which organization an authenticated user is currently operating in, validating all organization choices against that user's memberships.

## Scope delivered

- Added a server-only tenant-context API that composes LMS-007 identity with the membership storage shared by LMS-008.
- Added a database-independent resolver and stable fail-closed errors for unauthenticated identity, no membership, invalid explicit context, and unavailable membership storage.
- Validated UUID candidates against the authenticated user's exact membership and returned the role stored on that membership.
- Selected a deterministic default membership ordered by creation time, with organization ID as a tie-breaker. Explicit invalid candidates never fall back to another organization.
- Added the tenant-context test suite and registered it in GitHub Actions CI.
- Added the tenant-context guide and ADR-009; updated architecture cross-references.

## Out of scope

No PostgreSQL RLS, tenant isolation, query middleware, automatic organization query scoping, organization switching UI, authorization policy, product routes, or organization features were added. Those remain separately scoped work, particularly LMS-010 for tenant isolation.

## Security model

Authentication remains LMS-007's responsibility. The tenant API does not read cookies or accept a caller-provided identity. Organization IDs are untrusted candidates and become context only after a server-side membership lookup for the authenticated user's ID. The role is read from that membership. No active organization is persisted in client-controlled storage. Database errors are mapped to a generic 503 without internal details; malformed and non-member explicit choices share a generic 403 and cannot cause a fallback.

## Tests

`tests/tenant-context.test.ts` covers unauthenticated users, users without memberships, single and multiple memberships, explicit membership choices, organization-specific roles, forged organization IDs, malformed IDs, client-supplied roles, no-fallback behavior, deterministic defaults, database failures, and unknown stored roles.

## Assumptions

- The safe identity returned by LMS-007 and server-stored membership data are trusted inputs.
- With no explicit organization candidate, the earliest membership by `createdAt` is the MVP default; organization ID breaks timestamp ties deterministically.
