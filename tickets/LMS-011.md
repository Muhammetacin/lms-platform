# LMS-011 — Organization Settings

Status: IN PROGRESS

## Objective

Establish the first organization-owned application resource by allowing
authorized organization members to read organization settings and authorized
administrators to update the organization name.

## Scope delivered

- Reuse the existing `Organization` model; no schema or migration change is
  required.
- Add `GET` and `PATCH /api/organizations/settings` using LMS-007
  authentication, LMS-008 permissions, and LMS-009 trusted tenant context.
- Return only organization `name` and `slug`. OWNER, ADMIN, and MEMBER can read;
  OWNER and ADMIN can update the trimmed name; MEMBER cannot update.
- Reject client-supplied organization IDs, roles, and unexpected payload keys.
- Apply bounded strict name validation and existing same-origin JSON protection
  to cookie-authenticated PATCH requests.
- Add focused route/core behavior tests and include them in CI.
- Keep slug read-only until its normalization and case-insensitive uniqueness
  semantics can be defined consistently with a database invariant.

## Tenant ownership pattern

```text
Authenticated user (LMS-007)
        ↓
LMS-009 requireTenantContext() without a client candidate
        ↓
LMS-008 permission check against tenant.organizationId
        ↓
Organization settings read/update by tenant.organizationId
```

This establishes a real organization-scoped resource boundary but does not
complete tenant isolation. LMS-010 remains BLOCKED and must be reopened for
database-backed cross-tenant testing.

## Out of scope

Slug mutation, schema changes, organization switching, organization UI,
membership/employee/team/course workflows, branding, billing, integrations,
RLS, and general tenant isolation.
