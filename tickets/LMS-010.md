# LMS-010 — Establish Tenant Isolation

Status: BLOCKED

## Objective

Establish and prove tenant isolation for the LMS-012 organization-scoped employee management boundary, using LMS-007 authentication, LMS-008 authorization, and LMS-009 trusted tenant context.

## Repository inspection

- Read `AGENT_RULES.md`, product vision, database docs, tenant/auth/authorization/employee docs, ADR-001/004/009/010/011/012, and LMS-007 through LMS-012. `docs/04-architecture.md`, `docs/05-database.md`, and `docs/06-security.md` are not present; `docs/database.md` is the existing database source.
- Inspected Prisma schema/migrations, auth and membership stores, tenant resolver, authorization code, settings and employee routes/stores, tests, package scripts, and CI.
- `User`, `PasswordCredential`, and `Session` are global identity/authentication data. `OrganizationMembership` is tenant-owned; `organizationId`, `role`, `employeeName`, and `active` are specific to its one organization. A `User` may hold separate memberships in multiple organizations.
- Employee list, detail, update, and deactivate already receive the trusted tenant from `requireTenantContext()` and the production Prisma queries include `organizationId`. Client body keys for tenant and role are rejected. Route handlers do not accept tenant IDs in their URL paths or pass query/header tenant candidates to the resolver.

## Implementation prepared

- Extracted the production Prisma employee queries into `createPrismaEmployeeManagementStore()` while keeping the application store server-only and connected to the shared Prisma client. This lets integration tests call the exact production query implementation.
- Configured a PostgreSQL 16 service in CI, dedicated `lms_platform_test` credentials/database, migration deployment, and a new PostgreSQL integration-test command.
- Added `tests/tenant-isolation-postgres.test.ts`. It is designed to exercise real handlers and production store queries for both tenants, including foreign-ID GET/PATCH/deactivate, list isolation, generic foreign/missing-ID behavior, forged tenant/role fields, multi-organization membership-specific names and active states, global-email employee creation, inactive-only context denial, MEMBER authorization, last-owner protection, concurrent owner deactivation, and direct persisted-state checks.
- No schema or migration change is needed. The generated Prisma client, existing LMS tests, and application authorization behavior remain intact.

## PostgreSQL/RLS assessment

RLS is not used. The application uses one shared Prisma client with `PrismaPg` and pooled PostgreSQL connections. Tenant-sensitive operations do not all run in transactions, no transaction-local tenant variable is set, no safe membership bootstrap policy exists, and production runtime-role ownership / superuser / `BYPASSRLS` attributes are not defined or verified. Partial policies or pooled session state would be unsafe. Application query scoping is not equivalent to RLS. Future RLS requires a reviewed migration/runtime role split, safe bootstrap, transaction-local context on the same connection for every protected query (including background jobs), and pool/rollback verification.
