# LMS-010 — Establish Tenant Isolation

Status: BLOCKED

## Objective

Establish server-side isolation so authenticated users cannot read or mutate organization-owned data belonging to another organization, reusing LMS-007 authentication, LMS-008 authorization, and LMS-009 trusted tenant context.

## Inspection completed

- Read `AGENT_RULES.md`, product vision, database/authentication/authorization/tenant-context documentation, ADRs, schema and all committed Prisma migrations, security-related source modules, all API routes, existing tests, package scripts, CI configuration, and LMS-007 through LMS-009.
- The current schema contains `User`, `PasswordCredential`, `Session`, `Organization`, and `OrganizationMembership` only.
- Current API routes are authentication login/logout. There are no organization-scoped product routes or server actions.
- Database access sites query global auth records and membership data used by LMS-008/LMS-009. No tenant-owned business resource read/write/delete exists to protect.
- There is no tenant-aware query layer, database RLS, database integration test harness, or LMS-010 ticket in the inspected checkout before this file was added.

## Blocker

The acceptance criteria require actual cross-tenant read, update, delete, enumeration, and parent/child tests against tenant-owned data, while the scope explicitly prohibits implementing the product resources that could provide those real access paths. Adding a placeholder resource, generic key/value table, or artificial route would invent product semantics and could not be presented as protection of an actual LMS resource.

The existing `OrganizationMembership` model is an organization-scoped association and is needed to bootstrap authorization and trusted tenant context. Applying RLS or tenant query scoping to it without a separate safe bootstrap design could break that security chain. The shared Prisma/PostgreSQL connection has no tenant-scoped transaction boundary, and the deployed runtime role's RLS bypass properties are not established. An RLS policy cannot safely be claimed from the available evidence.

## Options

1. **Recommended:** keep LMS-010 blocked until a product ticket defines the first real organization-owned model and protected operations. Resume tenant isolation at that access boundary and add database-backed cross-tenant tests.
2. Narrow LMS-010 to a specific existing tenant-owned resource and its real API, if one exists outside the inspected checkout; the owner must identify it.
3. Approve the smallest concrete resource and protected operations for LMS-010, accepting a scope change so isolation can be tested against actual behavior.

Do not add placeholder models, APIs, or partial RLS as a workaround.

## Required decision

Confirm option 1, or identify the approved model and operations for option 2 or 3. Until then, no application or database tenant-isolation claim is made.
