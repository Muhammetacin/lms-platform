# LMS-016 — Team Membership

Status: CODE COMPLETE

## Objective

Introduce Team Membership as an explicit many-to-many relation between Teams and employees:

```text
Team
→ TeamMembership
→ OrganizationMembership
```

`OrganizationMembership` is the employee identity in this relation. The global `User` is not the Team member identity. A membership row carries the organization, Team, and employee membership IDs so PostgreSQL can enforce that both endpoints belong to the same organization.

## Product decisions

- An employee can belong to zero, one, or multiple Teams.
- A Team can contain zero, one, or multiple employees.
- There are no Team-specific roles.
- Only active employees can be newly added to a Team.
- Deactivating an employee does not delete existing `TeamMembership` rows.
- Operational Team member lists show active employees only.
- `OWNER` and `ADMIN` can add and remove memberships.
- `OWNER`, `ADMIN`, and `MEMBER` can view memberships; `MEMBER` cannot change them.

## Database design

`TeamMembership` has these required columns:

- `organizationId` — owning organization and tenant boundary.
- `teamId` — referenced Team.
- `membershipId` — referenced `OrganizationMembership` employee identity.

Database constraints enforce the relation:

- Unique `(teamId, membershipId)` prevents duplicate membership in one Team.
- `Team` has a candidate key unique on `(id, organizationId)`.
- `OrganizationMembership` has a candidate key unique on `(id, organizationId)`.
- Composite foreign key `(teamId, organizationId)` references `Team(id, organizationId)`.
- Composite foreign key `(membershipId, organizationId)` references `OrganizationMembership(id, organizationId)`.
- A separate organization foreign key references `Organization(id)`.
- Deleting an organization, Team, or `OrganizationMembership` cascades to its `TeamMembership` rows. Deactivation is an update and preserves those rows. Foreign key updates cascade.

Because both endpoint foreign keys include `organizationId`, PostgreSQL itself rejects cross-tenant TeamMembership combinations, even when a write bypasses the application handlers.

## API

```ruby
GET    /api/organizations/teams/:teamId/members
POST   /api/organizations/teams/:teamId/members
DELETE /api/organizations/teams/:teamId/members/:employeeId
```

The add request accepts only an `employeeId`, which must be the employee's `OrganizationMembership.id`. Repeated membership returns a conflict; missing or foreign targets use scoped not-found responses.

## Tenant isolation

- Tenant context is resolved server-side from the authenticated identity; request tenant fields do not select the organization.
- Team lookup is scoped by both Team ID and the trusted organization ID.
- Employee lookup is scoped by both `OrganizationMembership` ID and the trusted organization ID.
- TeamMembership list, add, and remove queries include the trusted organization ID.
- Forged `organizationId` and `tenantId` fields are rejected and are never trusted.
- Cross-tenant combinations are blocked by application-scoped lookups and by the PostgreSQL composite foreign keys.

## Authorization

Reads use the existing `VIEW_ORGANIZATION` capability. Add and remove use `MANAGE_TEAMS`.

| Action | OWNER | ADMIN | MEMBER |
| --- | --- | --- | --- |
| View Team members | Yes | Yes | Yes |
| Add employee | Yes | Yes | No |
| Remove employee | Yes | Yes | No |
