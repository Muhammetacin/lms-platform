# LMS-012 — Employee Management

Status: CODE COMPLETE

## Objective

Establish employee management on the existing organization membership relationship, using the authenticated user identity, LMS-008 authorization, and LMS-009 tenant context.

## Implementation

- Reused `OrganizationMembership` as the employee record; added organization-scoped nullable `employeeName` and `active` defaulting to true, plus a deterministic organization-list index. Added migration `20261005120000_employee_management`.
- Added `GET` and `POST /api/organizations/employees`, `GET` and `PATCH /api/organizations/employees/:employeeId`, and `POST /api/organizations/employees/:employeeId/deactivate`.
- New users are atomically matched/created by exact trimmed email and joined as MEMBER. Existing identities and other organization memberships are not changed. A new identity receives no credential; invitation and account activation remain LMS-014 work.
- PATCH changes only the organization-specific managed display name. Email is the read-only global authentication identity. Role changes and reactivation are not exposed.
- Deactivation soft-disables only the membership. It preserves the user, password credential, session, and other memberships. LMS-008 and LMS-009 now ignore inactive memberships. The last active OWNER cannot be deactivated; deactivation uses a serializable transaction, and OWNER targets require the existing owner-only capability.
- Responses expose only ID, email, name, role, and active state. Cross-organization and missing employee IDs share a 404. Request bodies reject role and tenant fields. Unexpected database errors are generic.

## Tenant boundary and LMS-010

List filters by trusted `tenant.organizationId`. Detail, update, and deactivation query membership by both `id` and `organizationId`; no global user lookup by employee ID is used. Creation's identity lookup is by globally unique email as required to reuse an existing authentication identity, then membership creation is tenant-scoped and atomic.

LMS-012 created the first substantial organization-owned employee boundary for LMS-010 to assess. It did not implement RLS, general query scoping, or database-backed cross-tenant tests. LMS-010 later implemented application-layer isolation and passed PostgreSQL verification for this employee boundary. See [LMS-010](LMS-010.md) and [Tenant Isolation](../docs/tenant-isolation.md).

## Tests

Added `tests/employee-management.test.ts` and a CI step. It covers unauthenticated and role behavior, tenant-scoped list/detail/update/deactivate, opposite-tenant IDs, client tenant/role tampering, multi-organization membership preservation, inactive context rejection, last-owner safety, validation, and generic storage failures.

At LMS-012 delivery time the repository did not configure a live PostgreSQL integration environment, and these behavior tests used the injected store. LMS-010 subsequently added a PostgreSQL 16 CI service and a separate integration suite that executes the production store.
