# LMS-090 — Employee Management UI

Status: CODE COMPLETE — AUTOMATED CI, COO REVIEW, AND CEO ACCEPTANCE PENDING

## Objective

Deliver a focused, responsive employee management experience in the existing Admin Portal by reusing the current employee, profile, import, authentication, tenant, and authorization APIs.

## Scope and acceptance criteria

- [x] Add Employees to Admin navigation and provide `/admin/employees` and `/admin/employees/[employeeId]` routes within the existing OWNER/ADMIN Admin Portal gate.
- [x] Show employee name, email, role, active/inactive status, job title, and department. The list remains deterministic and capped at the API's 100-record limit; the interface explains that search and filters apply only to the loaded records.
- [x] Provide accessible search by name, email, job title, and department plus active status and role filters, with loading, empty, error, retry, and no-match states.
- [x] Create employees through the existing endpoint with only email and name. New memberships keep the backend's default MEMBER role. Duplicate conflicts stay in the open form with an actionable message.
- [x] Read and edit organization-specific employee name, job title, department, phone, and employee number through the profile endpoint. Email, role, and active status remain read-only. Profile changes persist after reload.
- [x] Import CSV through the existing multipart endpoint and `file` field. Explain required/optional columns, 1 MiB and 500-row limits, and all-or-nothing behavior. Display useful file/header/row/field errors without echoing CSV values or claiming partial success.
- [x] Allow deactivation from the overview and profile with accessible confirmation, cancellation, pending state, clear errors, and last-active-OWNER protection. Do not offer deletion, reactivation, email changes, or role changes.
- [x] Reuse accessible Admin dialogs and success toasts. Dirty forms require an explicit discard choice; API and validation errors remain visible until resolved.
- [x] State clearly that invitation email delivery is not configured. The UI does not call invitation creation, expose activation tokens, or claim that an email was sent. LMS-052 remains separate.
- [x] Preserve trusted server-side tenant context, existing endpoint authorization, same-origin checks, payload allowlists, safe cross-tenant 404 behavior, and existing database models.
- [x] Add focused UI/core and browser coverage for navigation, create/edit/reload, import success and rejection, duplicate conflicts, deactivation cancel/confirm, invalid and foreign IDs, OWNER/ADMIN/MEMBER access, keyboard and responsive behavior, API failures, and unavailable invitation delivery.

## Implementation notes

- The Admin navigation is shown inside the existing Admin layout. That layout retains the OWNER/ADMIN gate; the APIs remain the authorization boundary.
- The existing bounded employee list projection now includes the already persisted organization-specific `jobTitle` and `department` values so the overview does not issue one profile request per row.
- Profile fields use the existing LMS-013 `GET/PATCH .../:employeeId/profile` endpoint. Optional values are normalized to `null` when cleared; read-only identity and lifecycle fields are not submitted.
- Imports use the existing LMS-017 contract, and API error codes are mapped to user-facing messages. The complete batch is rejected on any validation error.
- The UI uses the existing accessible Course Builder dialog and toast components. No dependency, schema, migration, authentication, session, or authorization changes were needed.
- The client never invokes `/invitation`; invitation delivery continues to return unavailable until LMS-052 supplies a real provider.
